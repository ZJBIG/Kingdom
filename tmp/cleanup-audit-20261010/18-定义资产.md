## 2. 加载方式判定结论（关键前置）

**结论：Datas 目录是"按类型整体递归加载"，不是按 id 硬编码引用。因此"grep 0 命中 ≠ 未使用"。**

证据：
- `Assets/Resources/Script/Data/DataBase.cs:12` `ResourcesPath = "Datas"`
- `Assets/Resources/Script/Data/DataBase.cs:63` `T[] loaded = Resources.LoadAll<T>(ResourcesPath);`
  → `Resources.LoadAll<T>` 递归加载 `Datas` 下**所有**可赋值为 `T` 的资产（含子目录、含子类）。
- `DataBase.cs:73-87` 以 `id`（Trim 后，OrdinalIgnoreCase）建索引；**id 为空会抛异常，id 重复会抛异常**。

由此推论（本次据此定判据）：
1. 任何 `.asset` 只要 `m_Script` 指向某 `GameDefinition` 子类，就一定会被对应 `DataBase<T>` 加载，与文件名/所在子目录/id 是否被 grep 命中无关 → **孤立定义不能用 grep 判定**。
2. 因此本次"占位/陈旧"的**主要判据改为字段层面**：id/Label/Description 是否为空、成本/产出是否全空、字段是否与当前 Data 类匹配、是否重复。
3. 另有两个例外加载点，与 DataBase 并列：
   - `Manager/StoryManager.cs:75` `Resources.Load<StoryArchiveDefinition>(...)`（按路径硬编码，见下）。
   - `Manager/TutorialManager.cs:211` `Resources.LoadAll<TutorialStepDefinition>("Datas/Tutorial")`。

`DataBase<T>` 在源码中的调用次数（证明各类型均在用）：Building 36、Research 36、Resource 23、SectorDefinition 17、WorkshopUpgrade 11、UltraProjectDefinition 1、RelicDefinition 1。

## 5. 重复定义清单

- **[置信度 Low] 跨类型同名同 id：`Building/Animal/Quarry.asset` 与 `Research/Animal/Quarry.asset`**
  - 证据：两者 `m_Name: Quarry`、`id: Quarry`、`Label: 采石场`；前者是 Building（`upgradeTo` 指向 e1c2d3e4…），后者是 Research（`BaseCost: 120`，描述"研究完成后解锁采石场"）。
  - 判定：**不是缺陷**。`DataBase<T>` 按类型分字典索引（`DataBase.cs:66-87`），Building.Quarry 与 Research.Quarry 落在不同字典，**不会触发重复 id 异常**；语义上二者本就成对（研究解锁建筑）。
  - 建议：保留观察（若未来需要跨类型全局唯一 id，需另行决策）。

- 其余：全仓 380 文件内**无**同类型重复 id、**无**内容近似重复（忽略 m_Name/id 后正文哈希一致者 0 组）。
