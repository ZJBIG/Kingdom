2. 不可违反的架构规则
======================================================================

2.1 定义数据
- Resource、Building、Research 等 ScriptableObject 只保存定义数据。
- 不保存当前数量、效率、进度、队列、自动建造进度或 UI 引用。
- ID 是代码和存档键；Label 只用于显示。
- 不使用显示文本、资源名称或反射字段作为存档键。

2.2 运行时状态
- ResourceState、BuildingState、ResearchState、GameState 是唯一权威状态。
- State 是 class，不是 struct。
- State 不引用 GameObject、Transform、TMP、Image、Viewer 或 Displayer。
- 普通外部代码不得直接写 State；写入通过 Manager 或 internal 方法。

2.3 Manager
- Manager 负责规则、验证、事务和 State 修改。
- Manager 不创建 UI，不持有 UI，不读取 UI 文本。
- 建造、拆除、自动建造与科研支付必须先完整验证，再一次性提交。
- 失败时不得发生部分资源变化。

2.4 SimulationManager
- SimulationManager 是唯一核心模拟时钟。
- 每次 Tick 显式接收 deltaSeconds。
- 相同初始状态、相同命令、相同总时间应得到相同结果。
- 结果不得依赖 Dictionary 遍历顺序。
- UI 激活状态不得影响模拟。

2.5 UI
- Viewer 负责页面、集合、选择和刷新调度。
- Displayer/View 只负责 Bind、Refresh、输入和调用 Manager。
- UI 不推进资源、建筑、科研、食物或日期。
- 隐藏页面不得持续格式化文本或触发布局重建。
- UI 动画不得成为游戏状态。

2.6 ExpantaNum
- ExpantaNum 只负责数字。
- ExpantaNumExtensions 只负责无状态通用数学公式。
- 不向数值核心增加建筑、科研、UI、时间推进或存档业务 API。
- 存档使用可 Parse 的 ToString()。
- 玩家显示使用 ToGameString()。
- 不重新引入 BigNumber 或兼容包装器。

2.7 Pair
- 真正的二元数据继续使用 Pair<T1,T2>。
- Pair 保留 first/second 序列化字段名。
- Save DTO 使用明确命名字段，不使用 Pair。
- 有第三字段、单位、独立验证、行为或版本需求时创建领域类型。

3. K3-01：模拟正确性收尾（最高优先级）

TODO K3-01-01：重写本 Tick 资源满足率
涉及：
- Manager/SimulationManager.cs
- Manager/BuildingManager.cs
- Manager/ResourceManager.cs
- Runtime/ResourceState.cs
- Runtime/BuildingState.cs

当前问题：
BuildingManager.CalculateEfficiency 只在资源 Amount == 0 时降低效率。
当库存大于 0、但不足以覆盖本 Tick 需求时，建筑仍按 100% 效率产出，
随后 ResourceManager 仅把资源 Clamp 到 0，造成一个 Tick 的超额产出。

目标算法：
1. 按稳定顺序收集所有建筑的潜在生成和潜在消耗。
2. 对每种资源计算：
   available = currentInventory + potentialProduction * deltaSeconds
   demand = potentialConsumption * deltaSeconds
   satisfaction = demand <= 0 ? 1 : Clamp01(available / demand)
3. 每个建筑的资源效率为其所有输入资源满足率的最小值。
4. 再汇总实际生成和实际消耗。
5. 最终资源库存不得低于 0。
6. 相同建筑以不同插入顺序创建时结果一致。

要求：
[ ] 不使用“库存大于 0 就 100%”。
[ ] 不允许先完整产出再 Clamp 掉不足的消耗。
[ ] 满足率为 0~1。
[ ] 没有输入资源的建筑不受资源限制。
[ ] 多建筑竞争同一资源使用统一规则。
[ ] 不在 Tick 中使用 LINQ、闭包或临时 Dictionary。
[ ] 使用稳定 orderedStates/定义 ID 顺序。
[ ] 为缓冲集合预分配并复用，容量有界。

验收测试：
[ ] 库存 1，本 Tick 需求 2，满足率和实际产出为 50%。
[ ] 库存 0、生产 5、需求 10，满足率为 50%。
[ ] 需求为 0 时满足率为 1。
[ ] 资源最终不小于 0。
[ ] 两个建筑竞争资源时总消耗不超过可用量。
[ ] 改变建筑创建顺序，10 秒结果一致。

TODO K3-01-02：食物每 Tick 积分，日期独立推进
涉及：
- Runtime/GameState.cs
- Manager/GameManager.cs
- Manager/SimulationManager.cs

当前问题：
GameState.AdvanceCalendarStep 同时推进一天和一次性结算 5 秒食物。
若玩家在第 4.9 秒建造或拆除农场，会错误按完整 5 秒的新速率结算。

目标：
- 每个模拟 Tick：
  FoodAmount = Max(0, FoodAmount + netFoodRate * deltaSeconds)
- 单独累计 calendarElapsedSeconds。
- 每累计 realSecondsPerGameDay 再增加 CalendarDays。
- 保存是否保留不足一天的余量需要明确；默认可暂不保存，但必须记录决定。

要求：
[ ] 食物积分与日期步进分离。
[ ] 建筑在任意 Tick 建造/拆除，只影响之后的时间。
[ ] 不同帧率运行相同总秒数结果一致。
[ ] 食物不低于 0。

验收：
[ ] 第 4.9 秒建造农场，5 秒时只获得 0.1 秒产量。
[ ] 第 4.9 秒拆除农场，前 4.9 秒产量不丢失。
[ ] 359、360、361 游戏日转换正确。

TODO K3-01-03：限制严重卡顿后的补算积压
涉及：
- Manager/SimulationManager.cs

当前 Advance 在达到 maximumTicksPerFrame 后保留全部 accumulatedSeconds。
长时间卡顿可能让后续很多帧持续补算。

要求：
[ ] 明确策略：Clamp backlog、丢弃超额，或转入离线/批量补算。
[ ] 默认建议 Clamp 到 tickInterval * maximumTicksPerFrame。
[ ] 输出 Development Build 警告，但避免每帧刷日志。
[ ] ManualTick 不受该限制。
