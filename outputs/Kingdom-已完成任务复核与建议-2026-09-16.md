### 1.2 缺口 A（成立，无测试覆盖）：暂停保存失败会在下次启动**多算**离线时间

- 机制：`applicationPausedAtUnixSeconds` **只在内存**（SaveManager.cs:200）。若 pause 时 `SaveNow(true)` **失败**（磁盘满/异常），主档保留旧时间戳，内存标记随进程消失。
- 后果：下次启动 `ApplyOfflineProgress`（SaveManager.cs:80）从**旧** `LastSaveUnixSeconds` 起算，把已经历过的暂停区间**再结算一次**。方向是**多给**（补算），不是漏给。
- 注意：正常路径（暂停保存成功）**不重复**——`SaveNow` 内 `MarkSaveTimestamp(saveTimestamp)`（SaveManager.cs:164）已把主档时间戳推进。
- 建议：给「暂停时保存失败」补一条有界回归（写入只读/满盘路径），断言重启后不重复结算。**本轮未改代码**，因为这是条件风险、且需运行验证才能证明修复有效。

### 1.3 缺口 B（成立）：未知/旧 ID 是「静默开新局并覆盖」，不是「拒绝主档」

- 机制：`DataBase<T>.Find` 对未知 ID 抛 `KeyNotFoundException`（DataBase.cs:35-42），经 `TryLoadSave` 的 `catch(Exception)`（SaveManager.cs:300）转为**新游戏**。
- 与交接文档「旧 ID 和未知 ID 直接使主档失效」的**差距**：主档文件既不删除也不标记；本次加载失败后开新局，**新档会写回同一路径，等于覆盖坏档**。
- 影响：玩家不会看到"存档损坏"提示，只看到进度归零。若产品希望"拒绝并保留现场"，需另行设计；当前行为与 v9「不留旧版迁移」的取向**自洽**，故本报告只标注差异，不主张修改。

### 1.4 缺口 C（成立，需产品决策）：「段存在但为空」被静默接受

- `ValidateRequiredSections` 只查 8 段非 `null`，不查内容。`Researches.States` 为空列表会被 `if (data.States != null)` 跳过循环后放行。
- **重要**：本条**不能**按字面收紧。`CreateRepresentativeSaveData`（KingdomLogicTests.cs:2430）本身就用空 `States`，且有 **32 处**测试经 `InvokeApplySaveData`/`LoadOrCreateGame` 走真实加载并断言**成功**（如 :334、:439）。
- 结论：收紧会**直接打破 32 处既有测试**，属回归而非修复。若确需收紧，必须**先改 fixture 再改校验**，并同步验收口径。本轮已实测该影响并**主动放弃**该修改。
