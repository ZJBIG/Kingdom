D01 [A / 高 / 并入 P0-04] 旧存档支持范围与磁盘加载入口不一致
------------------------------------------------------------
证据：
  Assets/Resources/Script/Data/SaveFormat.cs:3-4：MinimumSupportedVersion=5、CurrentVersion=8。
  Assets/Resources/Script/Manager/SaveManager.cs:544-547：接受 5 至 8 的版本号。
  同文件 :336-343：文件读取版本检查后，无条件 ValidateStorySection(data, true)。
  同文件 :362-371：Story 或 CompletedChapterIds 缺失时，requireSection=true 会抛异常。
  同文件 :240-246：直接 ApplySaveData 却调用 ValidateStorySection(data, false)。
  Assets/Tests/Editor/KingdomLogicTests.cs:1873-1905：版本 5/6 用例直接 InvokeApplySaveData，
  并非从文件执行 LoadOrCreateGame，绕开了更严格的 TryReadPath。
触发链：
  一个版本号受支持、其他段有效、但不含 Story 的旧格式文件
  → LoadOrCreateGame → TryLoadCandidate → TryReadPath → Story 必需检查拒绝
  → 备份同样不合格时进入新游戏分支。
影响：版本号被接受并不保证真实旧文件可加载；当前测试可能证明内部恢复函数有效，却未证明实际入口兼容。
反证/边界：
  当前 v8 缺 Story 应拒绝，不能为了旧档兼容直接删掉全部 Story 校验。
  本轮没有读取玩家实际旧档，因此不声称某个真实用户存档已损坏或曾经成功迁移。
最小验证：
  在隔离测试目录构造 v5/v6/v7 的有效其余数据、缺 Story，走公开 LoadOrCreateGame；
  再测 v8 缺 Story、空 ID、重复 ID、跳章 ID；分别断言兼容迁移与严格拒绝的合同。
建议：明确旧版本迁移政策；如承诺支持旧格式，进入完整校验前按版本补合法初始剧情历史，
      严守连续前缀，不凭空完成未来章节；如不支持，明确拒绝且保留文件，不无提示新建。
验收：真实磁盘入口、公开 API、无反射；迁移后重新保存 v8 再读可用，原旧文件仍可恢复。

D02 [B / 高 / 并入 P0-04] 备份恢复后的下一次保存会先用坏主档覆盖好备份
------------------------------------------------------------
证据：SaveManager.cs:123-129 从备份恢复不修复/隔离主档；:166-169 先写 tmp，
      再 File.Copy(SavePath, BackupPath, true)，最后 CommitTempSave；:215-220 替换主档。
      TryReadPath :322-324 的候选仅来自显式传入路径；LoadOrCreateGame 只尝试主档和备份，不尝试 tmp。
      KingdomLogicTests.cs:346-375 的备份测试在恢复后结束，没有检查“恢复后再保存失败”。
条件：主档 A 已坏，备份 B 有效；从 B 恢复；下一次 SaveNow 在复制 A→B 成功后、替换主档前失败或进程退出。
推演：B 被坏 A 覆盖；主档仍坏；tmp 即使有效也不被加载入口考虑。下次启动两个正式候选均失败。
反证/边界：若本次保存完整成功，新主档有效，不会立即丢档；不能把普通保存全部描述成不安全。
最小验证：隔离文件系统中先做坏主档/好备份；在“轮换备份已完成、主档尚未替换”处注入失败，重启加载。
建议：只有已验证的主档才有资格替换最后一份有效备份；从备份恢复时记录来源，
      将新主档成功提交与备份轮换作为明确阶段处理。保留或验证 tmp 可作为辅助，不应简单信任任意 tmp。
验收：每个关键 I/O 失败点后至少还有一个可加载正式候选；恢复后第二次保存和再次启动有专项用例。

D03 [B / 中高 / 并入 P0-04、P1-07] 暂停保存失败时，在线时间可能再被计入离线收益
------------------------------------------------------------
证据：SaveManager.cs:79-96 以 State.LastSaveUnixSeconds 到 now 结算离线；
      :158-174 仅提交成功才推进该时间戳；:198-207 暂停 SaveNow 返回值未用，恢复直接 ApplyOfflineProgress。
条件：最近一次成功保存后游戏在线运行了一段时间，暂停时保存失败，进程没有重启，然后恢复。
相对时间例：成功保存 t0 → 在线已结算 20 秒 → 暂停保存失败 → 后台 10 秒 → 恢复。
当前基线仍为 t0，离线输入会包含约 30 秒，而真正后台只有约 10 秒；额外部分来自已结算在线区间。
反证：正常暂停保存成功时基线正确；进程被杀后从旧快照重放又是另一种语义，不能简单把所有时间戳提前提交。
最小验证：用受控时钟/存储失败接口分别验证暂停保存成功、失败但进程存活、失败后进程重启；
          对比在线已结算量和实际后台区间，不依赖墙钟 sleep 或手工猜 Unix 时间。
建议：分清“最近持久化时点”与“当前内存已结算时点/暂停起点”，失败时持久化状态保持可重试，
      同时不能在仍存活的进程内重放已经结算的在线区间。
验收：连续前后台、保存失败重试、重启恢复均无重复收益，也不吞掉未持久化但应恢复的合法进度。

D04 [B / 中 / 并入 P2-04] 工坊提交异常的回滚只覆盖资源，不覆盖 Purchased
------------------------------------------------------------
证据：WorkshopManager.cs:118-124，提交回调先 state.SetPurchased(true)，再 RebuildProgression，未传 rollbackState。
      同文件 :275-283 重建全部效果并应用建筑派生状态；WorkshopUpgrade.cs:160-162 对未知效果类型抛异常。
      ResourceManager.cs:239-269 在提交异常时回滚资源，并且只通过可选 rollbackState 回滚外部域状态。
条件：工坊购买已经满足前置/资源，但效果重建或派生应用中抛异常。
推演：库存恢复，Purchased 可能保持 true；效果全量重建若中断，也可能与“已购买”标记不一致。
反证：本轮未发现现有资产正在使用未知效果类型；正常购买不会仅因缺资源触发该问题。
      ResourceManager 自身有可重入工作区与外部回滚接口，不应错误建议重写整个事务框架。
最小验证：以公开 ConfigureForEditor 创建受控异常工坊夹具，或给派生效果应用注入失败；
          确认购买前后资源、Purchased、效果对象、生产速率均保持旧值，再修复失败条件重试。
建议：复用现有 rollbackState 能力，补工坊域状态与派生效果的补偿；不只把 Purchased 改回去就结束。
验收：一次失败不留下免费购买/半份倍率，重试只收费一次；正常 observer 异常与提交异常分开处理。

D05 [A / 高，针对待实施方案 / 并入 P0-02] E08 会改变老工厂可再建造性，不只是新增选项
------------------------------------------------------------
证据：BuildingManager.cs:431-434 CanConstructNew 要求最高已解锁层级；
      :498-508 沿 UpgradeTo 查最高层；:604-609 拒绝被替代层级，返回 BuildingTierSuperseded；
      :998-1009 升级实际减少源建筑数量、增加目标建筑数量，并更新能力差。
      章程：CONTENTADVISE/e08-single-source-upgrade-chain-spec.md。
结论：一旦把三工厂挂上可解锁的升级链，旧层级会停止接收新建，不是玩家始终可自由补建两档工厂。
风险：章程漏掉铜线/陶瓷输出时，玩家把旧厂升完后可能无法再建旧厂补副产物；
      新厂所需高级材料难以凑齐时，低成本旧厂扩产选择也会提前消失。
反证：保留的旧建筑数量不会自动归零；玩家不升级仍可保留产能。但“旧厂可无限补建”的假设已经不成立。
最小验证：对每条新增链测解锁前、解锁后未升级、部分升级、全升级、拆掉最后一个老厂、存读档六种状态。
建议：先决定是升级替代还是并列建设；若保留现有替代语义，必须完整继承必要输出、明确转型代价与救援路径。
      不为迁就章程擅自改全局 CanConstructNew；该规则会影响其他 37 条已有升级边。
验收：每个阶段所有仍需副产物有可达且可扩产来源，不出现“科技完成反而锁死供应”的升级陷阱。

D07 [C / 中 / 收窄 P0-03-C] University → DeepSpaceObservatory 不是单目标科研升级
------------------------------------------------------------
证据：University 基础 RP 250，定向 RP 加成为 1.10/1.18/1.05/1.25；
      DeepSpaceObservatory 基础 RP 220，定向 RP 加成为 1.35/1.20/1.15。
      ProgressionModifierState 的这类倍率按 1 + Σ(value-1) 相加，不是把四个倍率连乘。
静态上限组合，在两者效率均为 1、相同全局因素且分别拥有已列定向效果时：
  University 单建筑贡献 = 250 × 1.58 = 395。
  DeepSpaceObservatory 单建筑贡献 = 220 × 1.70 = 374。
  后者少 21，约少 5.3%；生产力占用为 620 对 60，领土 440 对 12。
这是字段与公式推算，不是实际存档测量；可达购买组合、效率与是否跳到更高目标仍需验证。
重要反证：DeepSpaceObservatory.asset:27-29 同时给 FleetPower 60、Attack 120、Defense 160。
所以不能断言它被大学“全面支配”或应该简单提高科研倍率；它是军事/探索相关的复合设施。
此外大学有 UpgradeTo，观测站解锁后旧大学不能继续无限新建，旧审计的自由扩大学假设不成立。
建议：明确“科研扩张”与“军事观测”角色；对升级展示 RP 可能下降但战力上升的代价。
      只有正常流程中确实形成无法承担的科研墙，才选择数值或建筑角色修正。
验收：从合法进度布局中测试升级前后 RP、战力、约束与下一研究时间；不能只按每份 RP 一维评价。

      SectorManager.cs:475-491 区分本星系与跨星系门槛；既有设计约定本星系测绘即可开放本星系星区入口。
表现：只完成测绘时，手动星区页可有内容，但唯一下一步指引仍推舰队/跨星系研究。
反证：没有证明 UI 按钮真的锁住，因此不称为“本星系玩法不可达”；这是引导与现有可用玩法的顺序矛盾。
建议：在测绘后优先教一次可完成的本星系探索/供给/占领，再教跨星系；不提前改真实科技解锁。
验收：从只完成测绘的合法状态测试指引和导航；不需要开发者提醒即可发现本星系玩法。

D11 [B / 低至中，API一致性 / 并入 P2-04] 资源读接口按稳定 ID，事务接口却按对象引用
------------------------------------------------------------
证据：ResourceManager.cs:61-104 EnsureResource/TryGetStateByStableId 支持等 ID 的等价实例；
      :203-208 事务扣款只 states.TryGetValue(entry.Key)；:217-224 正向事务按对象键直接注册状态。
条件：调用方传入不同 ScriptableObject 实例，但 Id 与已注册资源相同。
结果推演：GetAmount(alias) 能返回原资源库存，TryApplyAtomicPayment(alias) 却视为无库存；
          TryApplyAtomicChanges 对 alias 正向入账还可能注册第二份同 ID 状态，增加保存/恢复歧义。
反证：当前常规资产加载大多使用 DataBase 的规范实例，未找到正常玩家操作必然构造 alias 的路径。
      全库定义 GUID/ID 干净也不会消除“运行时等价实例”的条件；这是 API 边界风险，不是现存重复资产。
最小验证：通过公开 SetIdForEditor 创建同 ID 资源别名；读库存、扣款、入账、存档，并检查状态个数。
建议：事务入口规范化到同一 ResourceState/定义并聚合重复项，或明确拒绝非规范实例且所有接口保持一致。
验收：读取可支付金额与实际交易决策一致；无同 ID 多状态；真实规范资产路径不受回归影响。

D12 [A / 中，数据口径 / 并入 P1-01] 首次科研指标会把“排队待支付”算作“开始研究”
------------------------------------------------------------
证据：ProgressionMilestoneRecorder.cs:80-81，在 ActiveResearch!=null 或 ResearchQueue.Count>0 时，
      就记录 FirstResearchStarted；:163 的目标把它当 150 秒内研究开始。
      ResearchManager.cs:476-507 明确存在队首缺料而尚未 CostPaid/尚未研究的状态。
影响：玩家只把缺料研究入队，指标就可能成功，掩盖真正等待资源的时长，误导开局节奏决策。
反证：如果这个指标本意就是“首次表达研究意图”，现有判断合理，但名称/验收口径应改清楚。
      当前 InitializeStartingBuildings 只 EnsureBuilding，并不赠送建筑数量；不能据此声称首建统计现在一定被起始建筑污染。
建议：分开 FirstResearchQueued、FirstResearchPaid、FirstResearchProgressed；
      使用真实进度/支付事件口径，不为改善指标修改游戏数值或赠送资源。
验收：缺料入队后仅意图指标触发；足额支付且 progress 实际增加后研究开始指标才触发；统计不改变 State。
